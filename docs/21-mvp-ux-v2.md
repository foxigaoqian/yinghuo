逝者智能体

MVP 产品体验优化方案 V2.0

从“创建一个数字亲人”升级为“把一个人慢慢留下来”

> 本版核心方向 不靠增加功能取胜，而是通过“无感账号、低门槛创建、渐进式记忆、状态恢复、家庭共建、主动关心和先体验后付费”，把整个产品做得更像一个长期使用的私人家庭空间。

适用阶段：0→1 MVP / 小团队快速验证 / 国内移动端与微信场景

# 文档摘要

本方案聚焦用户从第一次打开网站到长期回访的完整体验，不以“功能列表”为中心，而以“用户状态变化”为中心。核心目标是：让网络认知较弱的普通用户也能在 1–2 分钟内开始使用，并且在使用过程中自然建立身份、记忆、家庭关系和付费价值。

| 模块 | 核心结论 |
| --- | --- |
| 首次进入 | 不要求注册，自动创建匿名账户，直接进入体验。 |
| 创建 TA | 只问关系、名字、称呼；照片、声音、生平、性格全部后置。 |
| 记忆 | 聊天中自动发现候选记忆，必须由用户确认后进入核心记忆。 |
| 回访 | 自动恢复上次人物、聊天、草稿和历史，不把用户当成新用户。 |
| 主动消息 | 由人物习惯 + 近期聊天 + 重要日期 + 用户偏好触发，而不是机械定时。 |
| 家庭共建 | 邀请家人补充同一个人的故事、照片和声音，天然形成传播。 |
| 付费 | 先给可感知结果，再卖完整能力；不建议 MVP 一开始强推订阅。 |
| 移动端 | 微信环境识别、浏览器打开提示、可添加到桌面、草稿自动保存。 |
| MVP 范围 | 私人空间优先；公开社区、复杂社交和重型内容运营后置。 |

## 一句话产品定义

> 产品不是“数字人创建工具” 它应该是一处“家庭记忆空间”：用户可以先和 TA 聊起来，再在之后的日子里逐渐补充照片、故事、声音和重要日期；AI 的职责是帮助整理、记住和在合适的时候回应，而不是替用户编造人生。

# 1. 核心产品原则

| 原则 | 落地方式 |
| --- | --- |
| 先给价值，再要信息 | 先让用户开始聊、开始记录；手机号、完整资料、权限授权都尽量后置。 |
| 系统知道的，不让用户再填 | 访问环境、时间、用户ID、来源、上次人物等自动识别。 |
| 人物不是一次填出来的 | 人物资料通过后续聊天、家人共建、照片和声音逐渐形成。 |
| AI 不得把猜测变成事实 | 未经用户确认的推断和生成内容不得进入永久记忆。 |
| 用户做过的事必须留下痕迹 | 聊天、故事、照片、声音、重要日期都成为账户资产。 |
| 每个空状态都给下一步 | 没有照片、没有声音、没有故事，都要直接引导“添加第一份”。 |
| 第二次访问比第一次更重要 | 自动回到上次状态，而不是再次展示“创建 TA”。 |
| 复杂留给后台，简单留给前台 | 技术词、Memory、Persona、Embedding、UID 都不直接暴露给普通用户。 |

# 2. 用户状态机：产品应该围绕“状态”而不是“页面”设计

| 首次访问 | → | 匿名用户 | → | 首次创建 | → | 有记忆用户 | → | 回访用户 | → | 绑定用户 | → | 付费用户 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |

同时存在两条旁路：① 微信内打开 → 环境引导 → 浏览器/PWA；② 换设备或丢失本地身份 → 手机号/家庭编号找回 → 恢复原账户。

| 状态 | 用户看到什么 | 系统自动做什么 |
| --- | --- | --- |
| S0 首次访问 | 直接开始，不出现登录墙 | 创建 guest_id / family_id，记录来源与设备环境 |
| S1 创建人物 | 只填写关系、名字、TA如何称呼我 | 创建 person_id，初始化最小 Persona |
| S2 首次聊天 | 马上进入聊天，不要求先导入资料 | 建立会话，保存聊天，提取候选记忆 |
| S3 有资产的匿名用户 | 显示已留下的记忆、照片、聊天 | 保存长期数据，并适时提示“保护这份记忆” |
| S4 回访用户 | 直接看到上次的 TA 和“继续聊” | 恢复人物、历史、草稿和最近上下文 |
| S5 绑定用户 | 跨设备可恢复 | 手机号与匿名账户绑定/合并 |
| S6 家庭共建用户 | 邀请家人一起补全 TA | 关系权限、贡献记录、冲突处理 |
| S7 付费用户 | 解锁声音/高级生成等 | 订单、权益、历史结果写入账户 |

# 3. 首次体验：1–2 分钟内必须“聊起来”

推荐首条主路径：

进入网站 → 选择关系 → 填写名字 → TA怎么叫你 → 开始聊天

首屏不要出现复杂能力列表。第一次用户最需要知道的只有两件事：这个产品是做什么的，以及我现在能做什么。

| 步骤 | 推荐交互 | 不要做 |
| --- | --- | --- |
| 进入 | “你想记录谁？”：妈妈 / 爸爸 / 爷爷奶奶 / 爱人 / 朋友 / 其他 | 先注册、先看十几个功能入口 |
| 名字 | “TA叫什么名字？” | 要求完整姓名、出生日期、籍贯、职业等 |
| 称呼 | “TA平时怎么叫你？” | 显示 Persona / 角色设定等技术词 |
| 照片 | 可选，允许“以后再加” | 没有照片就不给继续 |
| 聊天 | 立即进入第一轮对话 | 要求先导入微信记录或填写生平 |

> 第一条硬规则 微信聊天记录、语音、相册、完整生平都只能是“增强项”，不能成为开始使用的门槛。零资料也必须能开始。

# 4. 无感账户：默认已经帮用户保存

第一次访问自动创建匿名账户。用户无需理解“注册”这件事，但系统应从第一条行为开始就能保存数据。

第一次访问 → 自动匿名身份 → 直接使用 → 产生记忆资产 → 提示保护数据 → 绑定手机号

手机号的价值表达不要写“完善账号”，应写成用户利益：

> 推荐文案 “保护这份记忆” 绑定手机号后，换手机也可以找回 TA、聊天记录、照片和故事。

建议提供一个可复制的“家庭编号”，仅在找回或客服场景展示。例如：萤火 8F26。它本质上是用户 ID，但对用户来说是可理解的产品语言。

# 5. 渐进式人物建立：让 TA 在使用过程中“长出来”

不要用一张长表单一次性收集人物信息。人物资料应该来自日常使用中的自然补充。

| 时机 | 前台提问 | 后台形成的数据 |
| --- | --- | --- |
| 第一次 | TA是谁？叫什么？怎么称呼你？ | 关系、姓名、称呼 |
| 聊过几次后 | “TA以前最常怎么关心你？” | 互动习惯 |
| 用户提到旧事 | “要把这段故事留下来吗？” | 核心记忆 |
| 合适的时候 | “要不要放一张你最喜欢的照片？” | 相册 |
| 用户已有音频 | “有 TA 以前的语音吗？可以保存下来。” | 声音素材 |
| 临近重要日期 | “这个日子对你们有什么特别意义？” | 纪念日 / 生日 |

> 体验目标 用户永远感觉自己是在“回忆和聊天”，而不是“维护数据库”。

# 6. 记忆系统：这是产品可信度的核心

这个产品里，AI 幻觉的伤害远高于普通聊天机器人。不能让模型为了“像”而编造共同经历。需要明确区分不同来源。

| 记忆类型 | 来源 | 是否可当作事实 | 处理方式 |
| --- | --- | --- | --- |
| 确认记忆 | 用户主动输入、上传记录、用户确认的候选记忆 | 是 | 可用于长期回答与主动消息 |
| 家人贡献 | 受邀家庭成员补充 | 条件性 | 标注贡献者；冲突时不自动覆盖 |
| 模型推断 | AI 从上下文推测 | 否 | 只能辅助理解，不写入核心记忆 |
| 生成内容 | 模型为了自然表达而创作 | 否 | 严禁自动转为永久事实 |

推荐的“候选记忆”体验：

用户聊天 → AI发现重要信息 → 生成候选记忆卡 → 用户确认 → 写入核心记忆

> 示例 用户：“妈妈以前每天晚上都会问我吃饭没有。” 系统：我发现了一段关于妈妈的记忆——“每天晚上都会问你吃饭没有。” [记下来] [不用]

如果用户问到系统没有的往事，推荐回答方向是承认不知道并邀请用户补充，例如：“这件事你还没有跟我说过，愿意讲给我听吗？”而不是编造具体地点、时间和共同经历。

# 7. 聊天体验：保持简单，但持续建立“被记住”的感觉

| 体验点 | 建议 |
| --- | --- |
| 首次开场 | 不要问一堆资料。可以从“今天突然想起 TA 的什么？”或温和的开放问题开始。 |
| 上下文连续 | 第二次打开能接上上次话题，不让用户重复解释。 |
| 草稿保护 | 输入中的长文本自动本地暂存，切后台/刷新可恢复。 |
| 记忆可见 | 允许用户查看“关于 TA 我们已经记住了什么”，并可修改/删除。 |
| 不强演 | 没有记忆就承认不知道，不假装“我记得”。 |
| 情绪强度 | 避免过度依赖式文案，不把系统描述成现实人物本身。 |

# 8. 主动消息：不要做成“定时机器人”

主动消息应该在用户已经使用几次后再询问是否开启。推荐选项：暂时不用 / 偶尔关心我 / 像以前一样。

> 主动消息公式 人物习惯 + 用户近期生活 + 重要日期 + 最近聊天 + 合适时机

| 触发来源 | 示例 |
| --- | --- |
| 近期事件 | 用户昨天说“明天面试” → 第二天问“今天面试怎么样？” |
| 人物习惯 | 用户确认“妈妈总问吃没吃饭” → 晚间偶尔自然关心 |
| 重要日期 | 生日、纪念日、节日等 |
| 长期沉默 | 一段时间没有回来 → 非强迫、低频提醒 |

关键点：不要每天机械重复同一句；不要在用户未授权前开启；不要让主动消息制造“真人正在现实世界持续观察你”的错觉。

# 9. 家庭共建：建议成为第二核心能力

一个人的记忆往往不完整。家庭共建既能提升人物真实性，也能形成自然传播，不需要生硬的“邀请好友”。

用户邀请家人 → 家人打开链接 → 自动临时身份 → 补充故事/照片 → 原用户确认/合并

| 设计点 | 建议 |
| --- | --- |
| 邀请文案 | “一起把妈妈的故事留下来”，而不是“邀请好友注册”。 |
| 受邀入口 | 打开链接即可先贡献，不要求先注册。 |
| 权限 | 默认只能补充，删除人物/导出数据等高风险操作仅管理员可做。 |
| 贡献记录 | 每段故事、照片、声音标注来源，便于处理冲突。 |
| 冲突记忆 | 不同家人描述不一致时保留来源，不自动覆盖成唯一事实。 |
| 隐私 | 创建者明确控制哪些内容可被其他家人看到。 |

# 10. 微信与移动端：必须做环境感知

目标用户主要从微信进入时，页面应该自动判断运行环境，并只在需要时展示场景化帮助。

| 环境 | 推荐体验 |
| --- | --- |
| 微信内置浏览器 | 右上角箭头引导“··· → 用浏览器打开”，允许关闭，数秒后自动消失。 |
| iPhone Safari | 在合适时机提示“添加到主屏幕”，不要首次打开就打断。 |
| Android Chrome | 支持添加桌面/PWA；安装后不再重复提示。 |
| 已添加桌面 | 直接以应用式体验进入上次人物。 |
| 网络中断 | 保存草稿、显示重试，不清空当前操作。 |

> 提示文案方向 “建议用浏览器打开，可保存到手机桌面。以后想 TA 的时候，直接点开就能回来。”

# 11. “我的”不做设置页，而做“我的家庭”

用户中心应该让用户看见自己已经留下了什么，而不是展示一堆账户字段。

| 区域 | 展示内容 | 空状态 CTA |
| --- | --- | --- |
| 人物卡 | TA 的照片、名字、最近一次聊天 | 无人物 → 创建第一个 TA |
| 记忆 | 已留下 X 段记忆 | 无记忆 → 写下一件小事 |
| 照片 | 相册数量 | 无照片 → 添加一张最喜欢的照片 |
| 声音 | 声音素材数量 | 无声音 → 上传一段旧语音 |
| 重要日子 | 生日/纪念日 | 无日期 → 添加一个重要日子 |
| 家庭成员 | 共同记录的人 | 只有自己 → 邀请家人一起补充 |
| 数据保护 | 手机号/家庭编号 | 未绑定 → 保护这份记忆 |

# 12. 付费体验：先证明效果，再收费

MVP 不建议一开始把“订阅”放在第一层。更适合从用户已经建立价值之后的增强能力收费。

| 能力 | 推荐漏斗 |
| --- | --- |
| 声音复刻 | 上传旧语音 → 免费短预览/试听 → 满意后解锁完整语音能力 |
| 照片动态化 | 上传照片 → 生成低成本预览 → 高清/完整版本收费 |
| 长内容生成 | 先展示一小部分可感知价值 → 解锁完整结果 |
| 高级存储/家庭空间 | 用户已经积累大量内容后，再提供更高额度或增强服务 |

所有支付状态都必须写入账户，而不是只保存在当前页面。支付成功后刷新页面、换设备，都应能恢复权益。

# 13. 状态恢复：判断产品是否成熟的关键

建议在测试阶段专门做“刷新测试”和“切后台测试”。每一个关键步骤都按一次刷新。

| 场景 | 正确体验 |
| --- | --- |
| 人物资料填一半刷新 | 恢复已填写内容 |
| 写故事时切到微信再回来 | 草稿仍在 |
| 支付失败 | 保留订单和输入，显示“重新支付” |
| 付款成功后刷新 | 权益和记录仍在 |
| 聊完第二天回来 | 直接恢复人物与最近上下文 |
| 换新手机 | 手机号验证后恢复人物、记忆、照片、声音、订单 |
| 新设备先产生临时数据后再找回 | 允许合并匿名账户，而不是覆盖丢失 |

# 14. 数据隔离与隐私：一开始就要设计

这个项目的数据比普通工具站更敏感。每一个人物必须绑定独立 person_id / family_id；记忆检索时必须带上用户和人物范围，不能只按语义相似度全库搜索。

| 风险 | 必须的产品/技术措施 |
| --- | --- |
| 人物串线 | 所有记忆、聊天、图片、声音均按 user_id + family_id + person_id 隔离。 |
| 家人权限过大 | 角色权限：创建者/共同编辑者/只读成员；敏感操作需更高权限。 |
| AI 编造事实 | 记忆来源分级，只有“已确认”记忆可作为真实背景。 |
| 隐私解释太晚 | 在上传照片、声音、手机号的位置即时说明用途与保存方式。 |
| 删除不彻底 | 提供人物/单条记忆/账号级删除路径，后台同步清理关联数据。 |
| 导出困难 | 用户应能导出自己的文字、照片索引和主要记忆内容。 |

# 15. MVP 功能范围：三人团队应该只做这一版

P0 是上线验证所必需；P1 在核心路径稳定后补；P2 暂缓。

| 优先级 | 功能 | 说明 |
| --- | --- | --- |
| P0 | 匿名账户 + 手机号绑定/找回 | 没有这一层，长期数据和回访体验无法成立 |
| P0 | 最小人物创建 | 关系、姓名、双方称呼 |
| P0 | 文本聊天 + 独立记忆库 | 先把“能聊且不串线”做好 |
| P0 | 候选记忆确认 | 防止 AI 自动污染长期记忆 |
| P0 | 聊天/故事草稿自动保存 | 移动端高优先级 |
| P0 | 我的家庭 Dashboard | 人物、记忆、数据保护、继续聊天 |
| P0 | 微信环境提示 | 符合国内真实入口 |
| P1 | 照片与相册 | 先存储与组织，AI 动态化可后续 |
| P1 | 家庭共建 | 验证自然传播和多人记忆价值 |
| P1 | 重要日期 + 主动消息 | 在已有真实记忆后上线 |
| P1 | 声音复刻预览与付费 | 作为第一批增值能力 |
| P2 | 公开社区/广场 | 审核与运营成本高，MVP 不做 |
| P2 | 复杂会员体系 | 先验证单项付费与长期留存 |
| P2 | 重型视频生成 | 成本与研发复杂度较高 |

# 16. MVP 阶段明确“不做”的事情

- 不要求用户先注册再使用。
- 不要求用户先导入微信聊天记录。
- 不把十几个字段做成一张人物创建长表单。
- 不把 Memory、Persona、Embedding、向量库等技术词暴露给普通用户。
- 不允许 AI 自行编造共同经历并当成长期事实。
- 不在首次进入就要求开启通知、主动消息、通讯录等权限。
- 不在 MVP 同时做公开社区、复杂评论、推荐流和内容审核体系。
- 不把付费放在用户还没看到任何效果之前。
- 不允许刷新、支付失败、切后台导致用户输入内容消失。

# 17. 上线后真正要看的数据

| 指标 | 定义 | 目的 |
| --- | --- | --- |
| 首次创建完成率 | 进入 → 成功创建第一个 TA | 判断第一步是否太复杂 |
| 首次聊天率 | 创建 TA → 发出第一条消息 | 判断是否真的“马上聊起来” |
| D1 / D7 回访 | 次日 / 7日内回来 | 判断陪伴与记忆是否有持续价值 |
| 候选记忆保存率 | 候选记忆卡 → 用户确认保存 | 判断自动发现是否准确 |
| 资料补充率 | 7日内补充照片/故事/声音的比例 | 判断渐进式建立是否自然 |
| 手机号绑定率 | 产生一定资产后 → 完成绑定 | 判断“保护记忆”价值是否成立 |
| 家庭邀请率 | 创建者发出家庭邀请的比例 | 判断家庭共建传播价值 |
| 主动消息开启率 | 出现邀请后选择开启的比例 | 判断主动陪伴接受度 |
| 付费预览转化 | 看到声音/照片预览 → 购买 | 判断增值能力真实价值 |

# 18. MVP 验收标准：不是“功能能点”，而是路径真的顺

| 验收场景 | 通过标准 |
| --- | --- |
| 新用户从微信进入 | 能看懂如何在浏览器打开；即使不操作也能关闭提示继续浏览 |
| 零资料用户 | 2分钟内可创建人物并发出第一条消息 |
| 不绑定手机号 | 核心体验仍可使用，数据在本设备持续存在 |
| 产生数据后绑定 | 原匿名数据无丢失，绑定后可跨设备恢复 |
| AI 不知道某件事 | 明确承认未知，不编造具体共同经历 |
| 聊天中产生重要信息 | 系统能提出候选记忆，用户一键确认或忽略 |
| 刷新/切后台 | 草稿和关键状态可恢复 |
| 家庭邀请 | 受邀者不注册也可先贡献；权限边界清楚 |
| 支付 | 失败可重试，成功后刷新/换设备仍有权益 |

# 19. 建议开发顺序

1. 先把匿名账号、person_id/family_id、数据隔离、恢复机制搭好。
1. 完成最小人物创建和文本聊天，让零资料用户可以 1–2 分钟开始。
1. 实现候选记忆 → 用户确认 → 核心记忆库，解决可信度。
1. 做“我的家庭”、空状态、草稿保存和回访恢复，解决长期体验。
1. 补微信环境识别、浏览器打开引导、添加桌面/PWA。
1. 上线照片/故事补充与家庭邀请，验证共建和自然传播。
1. 有真实用户后再做主动消息、声音复刻和付费预览。
1. 社区、复杂会员、重型视频生成等最后考虑。

# 20. 最终产品蓝图

无感进入 → 开始聊天 → 留下记忆 → 再次回来 → 家庭补全 → 长期陪伴

整个产品要让用户感觉：我不是在配置一个 AI，而是在一个安全的地方，慢慢把这个人留下来。

> 产品最终要追求的感觉 第一次来：很容易开始。 第二次来：它还记得我。 用久以后：这里已经有很多属于我们家的东西。 换手机时：我不用担心丢。 邀请家人时：我们可以一起补全。 付费时：我已经看到了价值，而不是被要求先赌一把。

## 附：开发与产品讨论时的统一判断标准

- 这个步骤真的必须现在让用户完成吗？
- 系统已经知道的信息，为什么还要让用户填写？
- 用户完成这个动作以后，页面和账户有没有留下可见变化？
- 刷新、切后台、换设备以后，这一步还能恢复吗？
- 这是用户能理解的语言，还是程序员语言？
- 如果用户什么资料都没有，还能不能开始？
- 如果 AI 不知道答案，它会不会为了自然感而编造？
- 这个功能是在增强核心关系，还是只是在增加功能数量？
