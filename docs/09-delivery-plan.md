# 开发任务、验收与上线计划

## 1. 排期方式

按一个人负责研发估算，不把三人团队当三名全职工程师。先完成两天技术小样，再依据真实速度排期。以下是有效研发工作日的粗估，不含等待主体、微信 H5 支付开通、平台审核或供应商开通，也不是交付承诺：M0约2–3天，A约10–15天，B约15–25天，C约10–20天，D约5–10天；另预留约25%联调与修复。兼职开发按每周实际可投入工作日换算。

前两周目标只锁定A的主要链路：一个TA、第一条记忆、一次可信文字对话、回访查看与导出。不要先做完所有视觉页面再找后端接，也不要在支付和退款没跑通时宣传开卖。

## 3. 后台必须交付的8个模块

| 模块 | 主要页面/字段 | 可执行操作 | 权限与留痕 |
|---|---|---|---|
| B01 用户与空间 | 脱敏账号、TA、成员状态、权益概况 | 查归属、处理账号申诉 | 不显示私人聊天；绑定变更需验证记录 |
| B02 商品与权益 | 商品版本、售价、规格、渠道、可售开关 | 发布新版本、停售、补偿grant | 发布后不可改旧快照；价格权限独立 |
| B03 订单与对账 | 实付、支付交易、抵扣、交付、退款 | 查单、退款审批、处理重复实收 | 金额/理由/执行人可追溯 |
| B04 生成任务 | Task/Attempt、供应商ID、成本、缺失输出 | 查状态、只补失败项、停止新售 | 不能无幂等复制同一付费任务 |
| B05 声音质检 | 素材授权、检查结果、试听、修改原因 | 要求补材料、修正、停用音色 | 只看被授权附件，访问有审计 |
| B06 社区审核 | 待审版本、举报、公开素材、处理原因 | 发布、拒绝、撤回、申诉处理 | 审核的是公共副本，不扫描私聊 |
| B07 客服售后 | 本人工单、订单任务关联、处理时限 | 回复、返工、转退款、关闭 | 用户授权才附素材，避免客服重复问订单号 |
| B08 数据与授权 | 导出/删除任务、撤权、备份恢复记录 | 重试、查看进度、处理失败 | 无任意批量下载全库按钮；破坏操作二次确认 |

研发/财务、客服、社区审核、素材质检分别授权；一个人可兼任多个角色，但日志需保留当次身份与动作。暂停模型服务时，客服仍可处理历史订单。

## 4. 发布前关键验收

| 编号 | 场景 | 通过标准 |
|---|---|---|
| AC01 | 无头像创建TA | 仅称呼即可进入聊天；无虚构过往首句 |
| AC02 | 同账号并发免费创建 | 最多一个免费active；其他成为明确提示的draft |
| AC03 | 账号A访问B的TA/文件/聊天 | API拒绝且不泄露正文、链接或对象存在细节 |
| AC04 | 同TA成员读取他人私聊 | 包括owner均不能读取 |
| AC05 | 双邀请最后一个名额 | 原子化，只接受一个新成员 |
| AC06 | 移除成员/撤AI授权 | 新读取与检索立即拒绝；在途输出复核；旧短链风险有边界 |
| AC07 | 上传中断与容量竞争 | 预留不会永久占用；两个上传不超容量；旧内容仍可读 |
| AC08 | 发消息后断网/刷新 | 用generationId恢复，无重复用户消息和双份助手回复 |
| AC09 | 更正记忆 | 后续对话用当前确认版本，不篡改历史原音 |
| AC10 | 十次重复支付回调 | 一笔支付、一次grant、一次交付，不重复消费抵扣 |
| AC11 | 用户付款后关闭网页 | 任务仍继续，作品/订单入口可找回 |
| AC12 | 供应商提交超时但已受理 | 先查状态，不盲目新建；不能重复付供应商费 |
| AC13 | 4张仅成功2张 | 显示部分完成，仅补另2张，不能误标全交付 |
| AC14 | 并发升级与留声抵扣 | 同一来源价值最多消费一次，金额均以分计算 |
| AC15 | 退款成功/失败/回调晚到 | 状态真实、恢复原权益一致、不吞款、不重复退款 |
| AC16 | 年费到期/超容量 | 无新高级功能，旧记录能看和导出，无强制删记忆 |
| AC17 | 试听不合格/方言/多人声 | 售前说明原因；未交付不先收声音年费 |
| AC18 | 清空聊天时生成中 | epoch失效，旧任务输出不复活已清空对话 |
| AC19 | 发布和撤回社区内容 | 公开副本单独确认，撤回同步从流/详情/收藏失效 |
| AC20 | 导出中成员被移除 | 生成与下载均再验权限；禁止拿旧导出链接越权 |
| AC21 | 问候关闭/闰月/时区 | 不再发送已撤销计划；显示下次实际日期 |
| AC22 | 两种H5容器基础交互 | 普通手机浏览器与微信内置浏览器的键盘/大字号/录音拒权/下载/支付返回可恢复 |
| AC23 | 数据库恢复 | 恢复成功，支付对账和删除墓碑重放完成 |

测试重点放在隔离、金额、状态和恢复。数据/交易集成测试使用真实PostgreSQL测试库与伪造供应商；支付测试环境与正式小额核对分开记录。端到端跑任务路径，不能仅写“按钮点击后出现文案”的测试宣称业务通过。

## 5. CI与运维门槛

代码开始后CI建议：锁文件安装→lint/typecheck→核心单测→数据库迁移/权限/交易集成测试→H5构建→H5主要流程E2E。V1覆盖H5在iOS/Android普通浏览器与微信内的已启用支付通道；V2再增加小程序编译和wx.requestPayment验收。

收费前至少监控：未交付已付款数、Outbox积压、队列最老任务、供应商未知状态、退款超时、异常重复回调、容量预留泄漏、模型成本/错误率。站内提示必须与真实故障相符；新售可暂停，已有订单持续可查。

初始恢复目标建议RPO≤24小时、RTO≤4小时；支持PITR时争取更短。它们是内部目标，必须做恢复演练并记录实测。生产支付账本另有渠道对账补偿，不能只依靠一天一次备份保证资金一致。

每次发布含数据库迁移兼容说明、开关变化、回滚方式和已售权益影响。出现越权、错扣款或授权失效仍生成，立即关闭相关新操作，保留查阅/售后入口，并据事件范围修复。

## 6. 三人分工

- 研发/产品：决策、接口、前后端实现、质量门槛、模型/支付验证。优先修阻止用户完成任务的问题。
- 产品/用户运营：家庭访谈、材料指导、试听质量、客服与返工、社区审核、退款原因归类。
- 社媒推广：授权案例、渠道落地、分场景内容、转化追踪；长期SEO围绕真实工具和记忆记录问题，不公开私人空间。

每周一次30分钟评审只看：完成的实际任务、最严重失败、转化原因、成本和下周一个主要目标。用户反馈按场景和影响归类，不按谁声音大直接往52页里加功能。

## 7. 给下一轮开发者的第一条任务

先完成M0-01、A-01及API契约生成，提交一个只在移动端H5打开的“创建TA→保存一条文字记忆→再读取”纵向小样，并在普通手机浏览器与微信内置浏览器各跑通。模拟数据要标识；未接模型时不能用固定脚本回复冒充AI接入。完成后再接真实文本模型和私有文件；小程序迁移另立V2任务。

本轮只交付文档，不创建付费云资源、不初始化真实支付、不提交虚构完成的应用代码。后续PR应注明涉及的P编号/API/AC编号与实测结果，便于产品伙伴按任务验收。
